# ADR-009：固定的核心分类与系统账户 seed

- 状态：已接受
- 日期：2026-09-14

## 背景

P2-004 已经创建分类和账户表，但尚无业务 seed。若让每个实现者或每个新 profile 自行决定系统分类、顺序、记录类型和默认账户，就会造成 UI、记录校验、JSON 导入和测试 fixture 不兼容。旧 v3.1 的 LedgerStore.StandardCategories 已表达了一组长期使用的个人财务分类；Java 版需要能稳定升级和测试的明确版本。

## 决策

1. 每个 ledger.db 在 V004 core_catalog_seed migration 中写入 core-catalog-v1 规定的 71 个系统分类、65 个分类类型关联，以及固定 UUID 的系统账户“现金储备”。
2. 系统分类 ID、父子关系、全局 sortOrder、可用财务记录类型、默认确认方式和推荐折旧方式固定在 docs/contracts/core-catalog-v1.md。实现不能按名称动态生成 ID，不能擅自增删 seed。
3. 沿用 v3.1 的完整 StandardCategories 作为本期分类范围，而非缩减为一组新“最小分类”。无类型系统父分类只用于分组，不能作为记录分类；无类型活动自定义分类仍可用于全部六类财务记录。
4. 系统账户初始为 CASH/ASSET、0.00、计入可用现金，openingOn 使用 V004 执行机器本地日期。它可由用户编辑名称、种类、期初值和现金标记，但不可归档。
5. V004 使用普通 INSERT，冲突时整个 migration 回滚，绝不覆盖 P2 预发行数据库中可能手动存在的数据。它不写 processed_operation，也不改变现有 dataRevision；后续用户 mutation 才改变 dataRevision。

## 备选方案

- 只 seed 少数“收入、餐饮、现金”项：上手略简单，但破坏与 v3.1 的等价范围，也会让后续导入和 UI 默认行为分裂。
- 根据名称运行时生成 UUID：实现短，但名称更名、翻译或大小写变化会改变身份，无法安全引用和迁移。
- 每次打开 profile 时补齐或覆盖 seed：能补修缺项，却会覆盖用户允许修改的系统账户，也把启动变成隐式业务写入。
- 不提供系统账户：用户每次必须先创建账户，简单收支录入缺少默认去向；与旧版“现金储备”体验不等价。

## 后果

- 优点：新的 profile 有立即可用、可测试和与旧版一致的基础分类；记录校验、前端展示、迁移和 fixture 可以共享稳定 ID。
- 成本：V004 是不可修改的已执行 migration；日后新增/弃用系统分类必须以新的 forward migration 和新的 seed contract version 完成，不能编辑 V004 或复用 ID。
- 风险：手工写入 P2 物理表且与 seed 冲突会阻断升级。该路径没有公开 UI，采取回滚保护比静默覆盖更安全；需要人工恢复或未来专门迁移。
- 反转路径：后续可新增 V005+ 将某个系统分类归档或引入新分类，但必须保留旧 ID 和历史记录引用；不得重放或重写 V004。
