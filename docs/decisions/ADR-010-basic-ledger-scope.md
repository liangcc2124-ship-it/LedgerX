# ADR-010：基础记账版范围收敛

- 状态：已接受
- 日期：2026-09-14

## 背景

LedgerX 仅供个人自用和小范围非商业分享。此前按 v3.1 全功能等价规划，使基础记录实现同时依赖资产/分摊、指标/公式、报表/预警和旧 JSON 迁移的完整公共契约。那些能力会显著增加接口、事务、测试和恢复复杂度，却不是形成可用记账软件的必要条件。

用户明确要求只实现基础功能，不引入金融安全或金融合规需求。现有前后端分离基座、profile、设置及 SQLite 核心表已经具备继续实现基础记账闭环的条件。

## 决策

1. 当前产品里程碑定义为“基础记账版”，不是 v3.1 全功能等价版。
2. 基础版只开放三类记录：`INCOME`、`FIXED_COST`、`VARIABLE_COST`。
3. 每条基础记录必须选择活动分类和活动账户，结算方式固定为 `PAID_FROM_ACCOUNT`；请求仍显式携带 `settlement.mode`，以保持字段语义明确。
4. 基础记录请求和响应不包含 `metricIds`、`allocation`、`fixedAsset`、应付款或公式字段。后端只写 `finance_record`、`ledger_meta` 和 `processed_operation`；高级领域表保持为空。
5. 基础版提供记录列表、详情、新建、完整编辑、移入回收站和恢复。不提供永久清理、批量修改、批量删除或批量恢复。
6. 账户余额继续由期初余额与活动、已结算基础记录实时投影，不存累计余额。删除记录取消其余额影响，恢复后重新计入。
7. G-002、G-003、G-004 不再阻塞基础版；它们整体降级为用户明确提出高级能力后才启动的后续设计。
8. G-005 的旧 JSON 导入和应用内备份/恢复不再阻塞基础版。当前备份方案是完全退出应用后复制整个 `%LocalAppData%\LedgerX` 目录；恢复时先保留当前目录副本，再整体替换。
9. 不新增角色、审批、操作审计、加密、风控、监管报送、联网身份或商业发布流程。已实现的 loopback 绑定、会话令牌、Electron sandbox/CSP 和参数化 SQL继续作为桌面应用技术边界，不扩展成金融安全体系。
10. 已创建的高级领域表和历史设计文档暂时保留，避免无价值的逆向迁移；system capabilities 和 Vue 导航不得宣称这些能力可用。

## 备选方案

### 完整实现 v3.1 等价能力后再交付

不采用。它需要先完成四组大接口和跨模块计算，交付时间与维护负担明显超出个人使用目标。

### 删除全部高级领域表和历史设计

不采用。V003 已落地这些表，删除会引入新的 schema 迁移和兼容风险；空表不会影响基础记录运行。

### 将所有业务放到 Vue 或 Electron 中以减少 Java 工作

不采用。这会破坏已经验证的前后端分离和 SQLite 单写者边界，并造成余额规则重复。

## 后果

- P3 分类/账户可以按原计划实施；随后直接进入 P4 基础记录，不再等待 G-002/G-003。
- 基础版更快形成可观察闭环：新增收支、重开、编辑、删除、恢复、余额变化。
- 旧 v3.1 数据不会自动迁入；需要旧数据时继续使用旧程序，或以后单独启动迁移设计。
- 高级表存在不代表功能可用；它们必须保持无公开 API、无入口、无 capability。
- 如果未来明确需要固定资产、分摊、指标、报表、预警或自动备份，先重新确认需求，再恢复相应模块/API/Task Spec，不得从历史草案直接编码。
